# Data Labelling — How Ground Truth Is Produced

Short, precise account of how the supervised labels for the AIOps experiments are
produced, as actually implemented. Labels are **generated by controlled fault
injection, never hand-annotated**: a known fault is injected into a known service
over a known time interval, that record is the ground truth, and it is joined back
onto the telemetry windows. Two paths — live and synthetic — emit the *same* label
schema, so the offline and online pipelines are identical.

## The label schema

> **Definition.** A labelled sample is a per-service telemetry **window** carrying a
> ground-truth `fault` (the injected fault type, or `normal`) and a `service` (the
> emitting service). An episode's injected root-cause service is recorded alongside
> for the localisation task.

Carried on `collectors/telemetry.py::Window` as `fault` (`# ground-truth label`)
and `service`. The live labels CSV schema is `fault, root_cause, start_ts, end_ts`.

## Live path — real cluster

**`faults/run_episodes.py`** drives an experiment as a sequence of **episodes**:

- **Normal episode** (~40%, `--normal-ratio 0.4`): no chaos, a labelled quiet
  period — the negative samples.
- **Fault episode**: inject a fault into a fixed target service via **Chaos Mesh**
  (`kubectl apply` a scenario YAML) on the movie/actor/review subtree, or via
  **Pumba** (`deploy/virtfusion/vm2-services/inject-fault.sh`) on the 9-service
  compose mesh. The fault→target mapping is fixed in `SCENARIOS`
  (e.g. `latency_spike → review-service`, `cpu_saturation → actor-service`).

For each episode it records **exact start/end timestamps**, the **fault type** and
the **targeted root-cause service** to `data/labels.csv`. That CSV is later
**joined by timestamp** onto telemetry windows pulled by the live collectors
(`collectors/telemetry.py` with `TF_LIVE=1`, over Prometheus/Loki/Tempo): a window
whose `ts` falls inside an episode interval inherits that episode's `fault`.

## Synthetic path — offline generator

**`ml/dataset.py`** mirrors the same join offline so the pipeline is identical.
Each window is emitted per service per timestep with its `fault` assigned by the
injection logic — one service is the injected `root`, ancestors on the call path
inherit a *secondary* `latency_spike`, everything else is `normal`. Two generators
are kept deliberately separate:

- **`generate_run`** (detection — RQ1/RQ3/RQ4): the label is `is_origin`; error
  spans are gated on it.
- **`generate_rca_run`** (localisation — RQ2): errors *propagate* up the call path
  and attenuate per hop, so `is_origin` is **not** consulted — otherwise a
  localiser weighting error spans would score a perfect 1.0 by construction. The
  origin is identifiable only as the root of the error tree.

## From labels to ML targets

**`ml/features/build.py`** writes the labels into the feature frame as
`label_fault` and `label_service`; `split_xy` then derives the training targets:

- **`y_binary`** = `(label_fault != "normal")` → anomaly detection.
- **`y_multi`** = `label_fault` → fault-type classification.
- **root-cause service** (`label_service` / the episode `root_cause`) → the RQ2
  localisation target.

## Why supervised? Can I use unsupervised?

You *can* use unsupervised methods — but only for one of the three tasks, and even
there labels are still required to evaluate.

- **Two of the three tasks are inherently supervised.** `split_xy` yields
  `y_binary` (is anything wrong?), `y_multi` (which fault type?) and the RQ2
  root-cause service. Unsupervised methods give only the first: "this window looks
  abnormal." They cannot name the fault class or point to the origin, because those
  categories are not discoverable from unlabelled structure — nothing in the raw
  telemetry says a cluster of anomalies *is* a memory leak or that actor-service
  *is* the root cause. Multi-class classification and the RQ2 error-tree localiser
  need a supervisory signal by definition.
- **Even pure detection needs labels — for scoring, not just training.** RQ1
  measures whether adding observability signals (C1→C4 in `features/build.py`)
  *improves* detection, and that measurement is `f1_score(y, model.predict(X))`,
  which requires ground-truth `y`. So even a fully unsupervised detector still needs
  injected known faults and recorded labels, purely to compute precision/recall/F1
  and attribute any difference to signal availability. Labels are the fixed
  measuring stick of a controlled experiment whose independent variable is which
  signals are present.
- **The repo already uses unsupervised ideas where they fit.** The online model's
  adaptive normaliser (`models/online.py::_EWStandardizer`) learns "today's normal"
  from normal windows and flags deviations; the torch-less `TemporalModel.predict`
  fallback flags any window with a standardised feature `> 2.5σ`. Both are still
  *evaluated* against the injected labels.
- **Unsupervised alone also struggles on this testbed.** Faults *propagate* and
  attenuate upstream, so every ancestor emits a secondary latency symptom — an
  unsupervised detector flags all of them and cannot separate origin from echo
  (exactly what the labelled error tree gives RQ2). And on a 9-service mesh most
  leaf services are normal, so severe class imbalance drowns the true positives
  (the LSTM baseline is class-weighted at `detectors.py` to survive this).

**Bottom line.** The labelling is not a modelling choice but an experimental-
measurement requirement: labels are needed to do fault-type classification and
root-cause localisation at all, and to *evaluate* every model — unsupervised ones
included — so the study can answer whether observability signals matter.

## One-line summary

> Labels are produced **by design, not annotation**: inject a known fault into a
> known service over a known interval → log `(fault, root_cause, start_ts, end_ts)`
> → join onto telemetry windows by timestamp → derive binary-anomaly, multi-class
> fault-type, and root-cause-service targets. The synthetic generator reproduces
> the identical scheme so offline and online experiments share one pipeline.
